# ORPHEUS development workflow

- Target build is Overwatch 1.74.0.0.104319. On `leafall`, follow the Doomfist and Wrecking Ball acceptance checklists in `docs/ROADMAP.md`. Reuse the same mechanisms and acceptance checks across heroes and maps. Prefer evidence from the target build and small changes to shared mechanisms.
- The default branch `main` is the community-maintained Python implementation. Base general Python work on current `main`, publish a topic branch and open a pull request to `main`. The `leafall` hero work keeps its dedicated branch and reaches `main` through a pull request. The separate `rust` branch and worktree hold the Rust implementation.
- Unattended tasks work on server code, data tools, tests, and documentation. Leave game startup, game controls, and client acceptance to the user unless the user explicitly authorizes a separate session.
- Keep each completed change focused. Inspect the working tree, run the relevant tests and checks, and review the staged diff. Update `CHANGELOG.md` in the same commit with the change, test results, client acceptance, and remaining issues. Use an English Conventional Commit such as `fix: retire obsolete body respawn timers` and add the trailer `Assisted-by: Codex` for Codex-assisted commits.
- Follow the [contribution guide](CONTRIBUTING.md) for Python and dashboard checks. Compare affected behavior with a reference replay or fixture when available. Record external research and upstream code sources in `docs/CREDITS.md`.
- For Python behavior changes, follow the [shared behavior contract workflow](docs/BEHAVIOR_CONTRACTS.md). Supply a synthetic or approved language-neutral fixture with inputs, expected outputs and provenance. Record unavailable prerequisites and pending original-client acceptance, and backfill older behavior as it is touched.
- Maintain the project-wide restoration checklist in `docs/ROADMAP.md`. Check off each item when repeatable evidence covers its stated scope and any required original-client acceptance has passed. Record partial progress and its limits in the changelog or verification record.
- Use the maintainer `leafall903` and verified GitHub noreply identity for maintainer-authored commits. Check the effective author before committing. Preserve contributor authorship when applying reviewed PR commits and retain previous authorship in published history.
- The publication repository is `https://github.com/leafall903/ORPHEUS.git`. Push general Python changes to their topic branch and hero work to its designated `leafall` branch. The inherited server remote is `upstream`. Work from the current public history in a source-only checkout and preserve the separate local research history.
- Before the first push, audit **every Git object reachable from the branch**, including historical files and commit metadata. Before later pushes, audit all outgoing commits and objects. Leave credentials, logs, captures, profiles, generated binaries, local caches, and unapproved third-party game assets or data off GitHub. A pattern in `.gitignore` affects untracked files only.
- Keep client research material and prepared runtime inputs in separate local storage. Validate that the publication checkout boots and serves the target scene with authorized external runtime data and no game installation or launcher DLL. Keep the existing upstream license notices and credits. The ORPHEUS contributor list is maintained separately in `docs/CONTRIBUTORS.md`.
- After a tested commit and a successful publication audit, push the reviewed change to its topic or designated development branch normally, then submit a pull request to the target branch. Respect the `main` and `rust` protections, including required checks and an up-to-date branch. Direct pushes or protection bypasses to those branches are prohibited. If authentication, the audit, branch protection or a non-fast-forward blocks publication, preserve the local commit, record the cause and continue local development. Avoid force pushes, remote deletion, history overwrites, automatic releases, and automatic version bumps.
- On the maintainer's development machine, run the strict Git history audit and headless startup probe on the exact publication candidate in the source-only checkout. Before updating an existing development branch, verify that its current remote head is an ancestor and confirm the new remote head afterward. For an initial Python topic branch, verify that it starts from the reviewed public `main`.
- Review community PRs on GitHub against current public `main`. Preserve contributor authorship and verify the resulting source-only commit. The public source checks and contributor setup are documented in `CONTRIBUTING.md`.
- At handoff, report the project status, branch, latest commit, changelog, test results, client acceptance status, and GitHub sync result.
